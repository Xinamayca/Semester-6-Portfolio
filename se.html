Why

We were assigned the LASR card exercise on day one as a way to align on quality attributes before making any architecture decisions. I had no idea what LASR cards were going in, so it was all new to me.

How

We went through the cards as a group, debating each one against our project context, the Humber Arboretum dashboard and field app. I contributed by thinking along and arguing for what made sense from a user perspective.

What

We landed on Usability, Functional Suitability, Scalability, Cost Efficiency, and Compatibility as our top 5:

  • Usability — we have two very different user groups, sustainability staff and regular visitors. If the system isn't easy to use neither group will actually use it.
  • Functional Suitability — the system needs to actually do what it promises. For an ecological monitoring tool that feeds into ESG reports the data and features need to be correct.
  • Scalability — the Humber Office mentioned they want the system to grow and eventually be maintained by their own staff. So it can't be something overly complex that only a developer team can touch.
  • Cost Efficiency — they also flagged low cost as a requirement. University sustainability office, not a startup with funding. The system needs to be affordable to run and scale.
  • Compatibility — the dashboard needs to work on desktop, the field app on mobile, and the system may need to connect with tools the Humber Office already uses.

Things like Reliability and Safety ended up lower, not because they don't matter, but they weren't the priority for our context.

After picking our top 5 we didn't just leave them as card titles either. We deepened each one into a proper definition with concrete measurements and priorities. So Usability for example became something specific like the interface needing to meet WCAG 2.1 standards and users being able to onboard within 2 minutes. The full quality attribute breakdown is included as a supporting document.

So What

The architecture lecture that followed went mostly over my head, but the baseline I took from it was that it's kind of like design, there's a structure to the decisions you make, it's just written in a language I don't speak yet. And honestly? I might never speak it. But understanding that software architecture follows similar patterns of intentional decision making as design is enough for me to keep up and contribute where I'm capable of this module.

Technology Choice: React Native

For the mobile application, we evaluated several cross-platform and native frameworks before settling on React Native.

Alternatives considered:

Looking at this through Hofstede, Austria scores 55 on Individualism, which is relatively high. In individualistic cultures people tend to maintain emotional distance from strangers and keep their personal and public lives clearly separated. This explains why Austrians do not greet strangers or make small talk the way people do in more collectivist cultures. Aruba does not have official Hofstede scores of its own but shares strong cultural similarities with neighbouring Latin American and Caribbean countries like Venezuela which scores just 12 on Individualism. That is a massive contrast. Coming from a culture that sits so far on the collectivist end of the scale, where warmth with strangers is simply the default, what I experienced as unfriendliness in Vienna is not actually rudeness in the Austrian cultural context. It is just a completely different baseline for how people behave in public.

That high individualism score made me feel really alone in the city. I even had a conversation with a classmate who was absolutely convinced Vienna was the best city in the world. Code Deep Dive — Dashboard Map

The following is a breakdown of the key parts of the dashboard map I built. I chose to go into detail on these specific sections because together they tell the full story of how the map works, from setting it up in the browser, to connecting to the database, to fetching the right data, to rendering it all visually on screen.

Each section covers a different layer of the component. Client Rendering — Line 1

'use client';

The very first line of the file. In Next.js components run on the server by default, meaning they get rendered before they even reach the browser. But a map cannot work on a server. It needs the browser to render the tiles, handle the clicks and interact with the user. Adding 'use client' at the top tells Next.js to run this component in the browser instead. Without it the whole map would break.

Leaflet Imports — Lines 4-6

import { MapContainer, TileLayer, Marker, Popup } from 'react-leaflet';
import L from 'leaflet';
import 'leaflet/dist/leaflet.css';

Line 4 imports the core React Leaflet components:

  • MapContainer is the wrapper that renders the actual map on the page
  • TileLayer loads the map tiles from OpenStreetMap, the visual layer you see
  • Marker places a pin on the map at a specific coordinate
  • Popup shows a small info bubble when you click a marker

Line 5 imports L, the core Leaflet library. This is used to create and customize the pin icons so they match the Terra brand instead of using the default Leaflet pins.

Line 6 imports Leaflet's CSS. This one is easy to forget but critical. Without it the map renders completely broken with no styling, overlapping tiles and misaligned controls.

The Search Feature

Typing a name in the navbar filters entries in real time and triggers a smooth fly-to animation on the map using map.flyTo with a 1.2 second duration. It automatically opens the popup and selects the pin at the same time. The search, the map movement and the pin state all coordinate together in one seamless flow.

This was actually one of the trickier parts to build. The issue was timing. When the map finishes flying to a location, the code needs to find the pin and activate it, open the popup and add the glowing ring. But Leaflet does not always render the pin's HTML element immediately when the map stops moving. It only renders markers when it needs to, called lazy rendering, which meant the pin sometimes did not exist in the browser yet by the time the code tried to find it.

The solution was a retry loop inside FlyToController:

retriesLeft: 10
setTimeout(retry, 200)

Instead of trying once and failing, the code tries up to 10 times waiting 200 milliseconds between each attempt. It keeps checking "is the pin there yet?" until it finds it and then activates it.

map.once('moveend') on line 64 makes sure the whole sequence waits for the fly animation to fully finish before even starting to look for the pin. Without that it would be trying to activate something that has not loaded yet.

Getting this right took some back and forth but the end result is a search that feels completely seamless.

Plain Language Explanation

What this actually is

Lab 6 built a contact storing program, but with one catch. Everything it remembered disappeared the moment the program restarted because it was only ever keeping a list in the computer's working memory. Lab 10 fixes that one problem. What actually changed

Picking up the metaphor from Lab 6, there is a front desk that receives every request and a storage clerk who does the actual storing.

The front desk did not change at all. It still receives requests, checks they make sense and passes the work along, exactly as before.

The storage clerk got replaced. Instead of keeping a paper list that gets thrown out whenever the office closes, the new clerk writes everything into a proper filing cabinet, a real database, that stays intact no matter what happens to the front desk.

The front desk never noticed the swap because it never talked to the list or the filing cabinet directly in the first place.
